# 使用反馈与 Gitee Issue

## 何时报告

先完成用户眼前能完成的工作，再判断这一例是否值得占用用户和维护者的时间。准备上报前，Agent 要能根据现有证据回答：“维护者可以检查技能的哪一处？这个案例能帮他作出什么改进或验证？”能具体回答才去查仓库；无法回答就在本轮处理，省去注册、整理附件和询问是否上报的步骤。已有持续发布授权也沿用这个判断。

| 遇到的情况 | Agent 的处理 |
|---|---|
| 用户说“这一镜再委屈一点”，或原稿准确、某次成片表情偏重 | 按创作要求改稿，或按[成片偏差的判断](prompt-revision.md#先判断偏差来自哪里)核对。原因未明时保留判断，不要求用户反复生成来凑案例。 |
| 输出偶尔漏写配角，当前规则已覆盖，改回原句即可 | 先补好这份稿。若发现主模板与校验规则相冲突，或已有不同输入显示同一检查会漏掉同类角色，就有了可上报的依据。 |
| 官方安装包引用了缺失的文件，或有清楚的输入能揭示现有规则处理不了的一类分镜 | 一个案例也足够。定位到文件、规则或缺失的能力，说明修好后应出现什么结果。 |
| 已有 Issue 描述同一原因 | 已有证据足够时到此为止。新案例能缩小触发范围、解释既有反例、补足关键材料或证明修复后回归时，才补到原帖。仅更换人名、剧本或素材不构成新增证据。 |

只有决定值得上报后，才为这个案例整理下面四项。用户只需要改稿、表示暂缓或不想注册时，回到原任务。

## 一条调优案例需要交付什么

正文用以下四个 Markdown 二级标题，各写一次。

| 标题 | 提交的内容 |
|---|---|
| `## 问题简述` | 用一两句指出哪一镜、哪个人物或哪个操作出了什么问题，预期怎样、实际怎样。说明偏差发生在提示词还是成片。能取到时附当时使用的技能短提交号，从安装目录的 `.gitee-revision` 或克隆安装的 `git rev-parse --short HEAD` 获取。 |
| `## 完整提示词` | 逐字收录产生问题的那一版，从【生成目标】到最后一行约束，保留全部镜号、台词、素材号和换行。用户提交过不同版本时标明实际用的是哪一版。精修任务若还涉及作为输入的原提示词，标明“输入原稿”和“本次输出”，各自给全。 |
| `## 完整剧本` | 提供该次输入的整份剧本。文档上传的附原文件；粘贴的保留全文、角色名、场次、对白和排版。若用户当时只给了一场，那一场的全部原文即为该次完整输入。给过整本则附整本。 |
| `## 参考素材` | 逐项附本次实际使用的原图、原音频、原视频、分镜图、首尾帧等，包括在同一对话前轮绑定且本次沿用的素材。每项保留当时的编号、用途和文件对应关系，如“@音频2 · 角色音色”。当时未编号的用原名和用途；仅预留的音色槽注明“仅预留，未绑定”。用户已提供且同意一并分享的问题成片可另标作“实际生成结果”。 |

全文可放在代码围栏内（围栏要比原文内部同类围栏更长），也可附原文件。媒体给可下载的原件；用 Issue 编辑器或宿主实际支持的附件入口上传，也可使用用户授权且维护者能打开的原文件链接。文件较多时可用一个 ZIP 保留原件，用目录区分同名素材，每项注明包内位置。编辑器返回的附件链接可直接用于 API 正文。逐项核对素材绑定，验证链接可由目标仓库的维护者访问。本机路径、缩略图或文件名不能交付原件。凭据和无关聊天记录不进入报告。

当次确实没有对应输入时，在该栏写明事实，如“本次未提供剧本”“本次未使用参考素材”；安装失败尚无提示词时写“本次尚未生成提示词”。已经用过但现在取不到的文件仍算缺件。先从本轮及已绑定的前轮材料找回，确实缺失时只向用户索取缺项，保留草稿。数据收齐后提交。

## 发布与补充案例

按使用者对目标仓库及本次完整材料的授权执行。已明确允许把这些内容发到本仓库，直接提交；若先前仅同意发送匿名摘要，先说明将向哪个仓库发送哪些原件，取得对完整材料的授权后再上传。对其他安装者同样按各自授权处理。

在[仓库 Issues](https://gitee.com/a1meon_admin/seedance25_prompt/issues)先检索相关的未关闭和已关闭问题，读最相关的正文和评论。确认有新增证据才向原 Issue 追加四项完整材料，在问题简述里写一句本例补充了什么。可使用已连接的 Gitee 工具或已登录的仓库网页直接提交。有终端凭据时也可用下列脚本；`create` 遇同标题只返回已有链接，确认值得补充后再用 `supplement`。附件先上传，将 HTTPS 链接写入 UTF-8 正文，每个原件占一行。打包时可在各行复用 ZIP 链接并注明包内路径。

```sh
python3 scripts/report_issue.py check --body-file /path/to/issue.md
python3 scripts/report_issue.py list
python3 scripts/report_issue.py create --title "简明的问题标题" --body-file /path/to/issue.md
python3 scripts/report_issue.py supplement --issue GITEE编号 --body-file /path/to/issue.md
```

核对远端正文或评论包含四项且附件可访问，再返回 Issue 链接。提交超时先读回原帖及评论，确认是否已经写入。无权限、附件上传失败或链接仅本人可见时，保留完整草稿，说明还缺哪一步。还要交付提示词时，反馈状态用独立消息发送。

## 第一次用 Gitee

只在确有上报价值、需要用户登录时给引导。用一句话说明“这份案例能帮维护者改进哪一处”，把 Issue 解释为“发给技能维护者的问题反馈”。Agent 先整理好可直接填写的标题、四栏正文和附件清单。按用户实际需要给下一步，已有登录就接着用。

1. **注册或登录。** 没有账号时给[个人账号注册入口](https://gitee.com/signup)，已有账号给[登录入口](https://gitee.com/login)。请用户在 Gitee 页面按提示完成账号和验证码操作。密码和验证码只在该页面填写。
2. **提交反馈。** 登录后回到[技能仓库的反馈页](https://gitee.com/a1meon_admin/seedance25_prompt/issues)。新问题点“新建 Issue”，选择“提交技能调优案例”，填写整理好的四栏并附原件；已有相关帖且确有新增证据时，直接给原帖链接，在评论区补充。网页方式无需学习 Git 或配置令牌。
3. **接手收尾。** 当前 Agent 能操作已登录页面且已获材料发布授权，就替用户填写、提交并返回链接。若用户在自己的浏览器操作，给可直接粘贴的内容和附件清单，由用户点击提交。用户愿意稍后处理时，把草稿留给他，继续当前创作。
